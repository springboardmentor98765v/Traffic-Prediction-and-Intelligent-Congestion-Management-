## 5. Known Limitations Going Into Milestone 3

1. **Synthetic data ceiling** — the historical dataset is still generated by a formula, not real sensors. A model trained on it will only be as good as the deliberately-built-in patterns (rush hour, weekday/weekend), not genuinely discovered real-world behavior.
2. **No cross-road effects** — congestion on one road never influences a neighboring road in this simulation, unlike real traffic networks.
3. **Road conditions are randomly simulated, not event-driven** — real closures/hazards would come from an actual incident-reporting system; this is a placeholder for that.
4. **Materialized view requires manual refresh** — `traffic_daily_summary` won't automatically reflect newly generated historical data; `REFRESH MATERIALIZED VIEW traffic_daily_summary;` must be run manually after regenerating data.
5. **TimescaleDB was deliberately not adopted this milestone** — if data volume grows substantially in Milestone 3, this decision should be revisited (see Day 1 notes for the original reasoning).

---

## 6. Recommended Next Steps for Milestone 3

1. If real sensor integration begins, the API contract (`/traffic/history`, `/traffic/features`, etc.) should remain the same — only the underlying data source changes, not what consumers expect back
2. Consider automating the materialized view refresh (e.g., a scheduled job) once historical data updates become more frequent than "regenerate once for a demo"
3. Revisit the TimescaleDB decision if data volume grows beyond what plain indexed PostgreSQL comfortably handles
4. Extend `road_conditions` to accept real input (e.g., an admin endpoint to report a closure) rather than only simulated data, once that becomes part of the scope
